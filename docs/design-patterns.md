# Design patterns

One row per pattern in use. Add a row (pattern, classes, reason) whenever a feature adds one.

| Pattern | Classes | Why |
|---|---|---|
| Repository | `user.repository.UserRepository`, `user.repository.RoleRepository`, `auth.repository.RefreshTokenRepository`, `org.repository.OrganizationRepository`, `org.repository.MembershipRepository`, `product.repository.ProductCategoryRepository`, `product.repository.ProductRepository` | All persistence goes through Spring Data repositories; services never write SQL. Product queries take the organization id, so tenant data is always filtered. |
| DTO + mapper | `auth.dto.UserResponse.from(User)`, `TokenResponse`, request records (`LoginRequest`, `RegisterRequest`, `RefreshRequest`) | Entities never reach JSON; a static `from(entity)` factory keeps the mapping in one place. |
| Chain of Responsibility | Spring Security filter chain configured in `config.SecurityConfig` (bearer-token filter, access handlers) | Each filter handles or passes on the request, so authentication and authorization stay separate from controllers. |
| DTO + mapper (paged) | `common.dto.PageResponse.from(Page, mapper)`, `org.dto.OrganizationResponse.from(Membership)` | Every list returns `{content, page, size, totalElements}` built from one mapper, so pages never expose entities. |
| Template Method (planned) | Webhook intake (M3+) | Shared verify, parse, dedupe, persist skeleton with a per-channel parsing step. |
| Strategy (planned) | `AssignmentStrategy` (M5+) | Round-robin, least-loaded and manual assignment behind one interface. |
| Adapter (planned) | `ChannelClient` (M4+) | One adapter per Meta channel, so the inbox never sees Meta's API. |
| Facade | `org.service.TenantAccessService` (`requireMembership`, `requireRole`, `hasAtLeast`) | One entry point for every tenant check, so features never touch `MembershipRepository` or the role order directly. |
| Factory Method (lightweight) | `org.service.InvitationTokenGenerator.issue()` returns `Issued(raw, hash)` | One call makes the random token and its SHA-256 hash together, so the raw token is handed out once and only the hash is stored. One product, so no abstract factory. |
| Observer | `org.service.InvitationCreatedEvent` published by `InvitationService.create` through `ApplicationEventPublisher`; `mail.service.InvitationMailListener` (`@TransactionalEventListener(AFTER_COMMIT)`) | Creating an invitation announces it without the service knowing who reacts. The listener emails the link only after the invitation is committed, so a rollback sends nothing. |
| Strategy | `mail.service.InvitationMailer` with `SmtpInvitationMailer` and `NoopInvitationMailer`, chosen once in `config.MailConfig` | The listener depends on one interface; SMTP is a variant, "not configured" is another, so no `if (smtp)` branch lives in the listener. Each variant has its own test. |
| Facade (signup flow) | `org.service.InvitationSignupService` (`preview`, `acceptAndSignUp`) | One call for the signed-out invitation flow: find the invitation, create the account, join the organization and start a session, all in one transaction. |
| Atomic claim | `setup.repository.SystemSetupRepository.claim` (`INSERT ... ON CONFLICT DO NOTHING` on the single-row `system_setup`) | Two first-run setups arriving together cannot both create an owner: the database picks the winner. |
| DTO + mapper (product categories) | `product.dto.ProductCategoryResponse.from(ProductCategory)`, request record `ProductCategoryRequest` | Category responses carry the organization id, never the `Organization` entity. |
| DTO + mapper (members) | `org.dto.MemberResponse.from(Membership)`, request record `UpdateMemberRoleRequest` | The member list shows user name, email and role without exposing the `User` entity or its password hash. |
| Adapter + Strategy (product images) | `product.service.ProductImageStorage` with `S3ProductImageStorage` (adapts the AWS S3 SDK client to any S3-compatible service: S3, R2, MinIO, ...) and `LocalProductImageStorage` (in-memory), both honoring `store`, `read`, `delete` and `publicUrl` (same contract tests); used by `product.service.ProductImageService`; chosen in `config.ProductImageStorageConfig` | Callers depend on one small interface and never see the S3 SDK. The S3 API is the adapter's outside system, and each service differs only by settings (endpoint, region, path style), not by code. The in-memory store is the second variant for dev and tests. |
| Adapter (Meta Pages) | `meta.service.MetaOAuthClient.listPages` and `subscribePage` (same interface and adapter as Meta OAuth) | `/me/accounts` and `subscribed_apps` go through the existing Graph adapter, so the page service never builds a Graph URL. Every page id is checked against the grant before any call is made. |
| Adapter (Meta OAuth) | `meta.service.MetaOAuthClient` (interface) with `meta.service.GraphMetaOAuthClient` | The Graph API and the Facebook login dialog sit behind one interface, so the service never sees HTTP or Meta's JSON, and tests replace the boundary. The adapter holds the app secret and logs failures without Meta's error text. |
| Adapter (Instagram) | `meta.service.InstagramOAuthClient` (interface) with `meta.service.GraphInstagramOAuthClient` | Instagram Business Login (api.instagram.com and graph.instagram.com) sits behind one interface, so the connect service never sees Instagram's HTTP or JSON. The adapter holds the Instagram app secret and reports failures without Instagram's error text. |
| Template Method (webhook intake) | `meta.service.WebhookIntakeService.receive` (skeleton: parse, verify, persist) with `meta.service.WebhookSignatureVerifier` | The skeleton is fixed: nothing is stored before its signature checks out, and deliveries for other products are ignored. META-06 adds the per-product parse step without changing the order. The signature secret is chosen by product, so one app's secret cannot validate the other's events. |
| Observer (message received) | `inbox.service.MessageReceivedEvent` published by `inbox.service.IncomingMessageService` through `ApplicationEventPublisher`, once per organization and newly stored message | The inbox announces a stored message without knowing who handles it: assignment, notifications and live updates listen with `@TransactionalEventListener`, so they see committed rows only. A Meta retry stores nothing and publishes nothing. |
| Template Method + Repository (incoming message) | `meta.service.WebhookEventProcessor` (routing) calls the persist step `inbox.service.IncomingMessageService.receive`; storage through `inbox.repository.*Repository` | Intake keeps one fixed skeleton (verify, store, route, dedupe, persist); the persist step finds or creates the customer and conversation per organization, channel and thread, and skips a provider message id the organization already has. Single responsibility: routing and persisting are separate classes. |
| Factory Method (product images) | `config.ProductImageStorageConfig.productImageStorage(S3StorageProperties)` | Picks the variant once at startup from configuration; prod fails fast when S3 is required and missing. |
| DTO + mapper (products) | `product.dto.ProductResponse.from(Product)`, request records `CreateProductRequest` and `UpdateProductRequest` | Create and update have separate request records; the response flattens the optional category to its id and name and never exposes the entity. |
| Specification (product list filters) | `product.repository.ProductSpecifications` (`inOrganization`, `inCategory`, `nameOrSkuContains`, `withStockStatus`), run by `ProductRepository` through `JpaSpecificationExecutor`; composed in `product.service.ProductService` | Each filter is one small predicate combined with AND, so a new filter is a new method and the list never grows string-built queries. `inOrganization` is always part of the query, which keeps tenant scope. The stock rule lives in `product.domain.StockStatus.of` and the repository tests check the SQL predicates agree with it. |
| Repository (locked query) | `product.repository.ProductRepository.findForUpdateByIdAndOrganizationId` (`PESSIMISTIC_WRITE`), used by `product.service.StockMovementService.record` and `product.service.ProductImageService.upload` (the image limit is counted under the same lock) | A stock change reads the product with a row lock inside the same transaction as its movement row, so two issues on one product run one after another and cannot overdraw stock. The lookup is scoped to the organization, so another tenant's product is "not found". |
| DTO + mapper (stock movements) | `product.dto.StockMovementResponse.from(StockMovement)`, request record `RecordStockMovementRequest` | The actor is shown as id and name only; the `User` entity and the movement entity never reach JSON. |
| Specification reuse (inventory summary) | `product.service.InventoryService` counts with `ProductSpecifications.withStockStatus` | Low and out-of-stock counts use the same predicates as the product list filter, so the summary and the list cannot disagree. |
| Observer (product deletion) | `product.service.ProductDeletedEvent` published by `ProductService.delete` through `ApplicationEventPublisher`; `product.service.ProductImageCleanupListener` (`@TransactionalEventListener(AFTER_COMMIT)`) | Deleting a product must also remove its stored image objects, but `ProductService` should not know about images. The event carries the object keys, read before the delete (rows vanish by ON DELETE CASCADE), and the listener deletes the objects only after the commit, so a rollback removes nothing. |
| Repository (product images) | `product.repository.ProductImageRepository` | Every query takes the organization id, so another tenant's images are never returned. |
| DTO + mapper (product images) | `product.dto.ProductImageResponse.from(ProductImage)` | The response carries a content path, never the object key or the entity. |
| Factory Method (messages) | `inbox.domain.Message.inbound(...)` and `Message.outbound(...)` | An inbound message always has a customer sender and an outbound one always has an agent, so each direction has one named constructor and no caller can mix them up. Enforced again by the `messages_inbound_has_sender` check constraint. |
| Strategy (session location) | `auth.service.IpLocator` with `MaxMindIpLocator` and `NoopIpLocator` | Turning an IP into a place name is a swappable step: a GeoIP database when one is configured, otherwise nothing. `RefreshTokenService` depends only on the interface, so a different database or provider is a new class, not a new branch. |
| Factory Method (session location) | `config.GeoIpConfig.ipLocator(GeoIpProperties)` | Picks the variant once at startup: the MaxMind reader when the database file exists, otherwise the no-op, so a missing file never stops the app. |
| Chain of Responsibility (session activity) | `auth.controller.SessionActivityFilter`, added after `BearerTokenAuthenticationFilter` in `config.SecurityConfig` | One more link in the Spring Security filter chain: it runs only once the token is verified, records the session as active and passes the request on. It never fails the request, so activity tracking cannot break an API call. |
| Specification + Repository + DTO (conversation list) | `inbox.repository.ConversationSpecifications`, `inbox.service.ConversationQueryService`, `inbox.dto.ConversationSummaryResponse.from(...)` | Each list filter (organization, channel, customer name) is a small predicate combined with AND, so a new filter is a new method, not a new branch in the query. Customers and last messages are loaded once per page, never per row. |
| Repository + DTO mapper (conversation detail) | `inbox.repository.ConversationRepository.findByIdAndOrganizationId`, `MessageRepository.findByConversationIdAndOrganizationId` (with `@EntityGraph`), `inbox.dto.ConversationDetailResponse.from`, `MessageResponse.from` | Every read takes the organization id, so another tenant conversation is never found, and the entity graph loads senders in the same query. `ConversationDetailService.find` is the one tenant-checked lookup other inbox features reuse. |
| Observer + Registry (live inbox updates) | `realtime.service.InboxRealtimeListener` (`@TransactionalEventListener(AFTER_COMMIT)` on `MessageReceivedEvent`), `realtime.service.RealtimeSessionRegistry`, `realtime.controller.TicketHandshakeInterceptor` | The inbox publishes an event and knows nothing about WebSockets; the listener pushes after commit and never throws into the publisher. The registry is the one place that knows which session belongs to which organization, so a broadcast cannot cross tenants. Revocation is the same Observer: `org.service.MemberRemovedEvent` (from `MemberService.remove`) is heard by `realtime.service.MembershipRealtimeListener`, which closes that user's sessions for that organization with `4003`; `org` never depends on `realtime`. |
| Observer (live inbox, client) | `frontend/src/lib/realtime.ts` (`startRealtimeClient`, `coalesce`), `components/realtime-inbox-refresher.tsx` | The browser subscribes to the server's `message.created` events and reacts with `router.refresh()`, so no component holds message state or polls. The client logic is plain functions with injected socket, ticket and timers, so reconnect, backoff and the 401 cap are tested with fakes. |
| Adapter + Factory + Template Method (outgoing messages) | `meta.service.ChannelClient`, `MessengerChannelClient`, `InstagramChannelClient`, `GraphMessagingClient`, `ChannelClientFactory`, `inbox.service.OutgoingMessageService` | The inbox sends through one `ChannelClient` interface and never sees Meta's API; the factory picks the adapter by channel, so a new channel is a new class. The shared base does the post and error mapping. The service saves only after Meta accepts and publishes the existing `MessageReceivedEvent` (Observer). |
| Adapter + Factory + Template Method + Observer (customer name and picture lookup) | `meta.service.CustomerProfileClient`, `MessengerCustomerProfileClient`, `InstagramCustomerProfileClient`, `GraphCustomerProfileClient`, `CustomerProfileClientFactory`, `CustomerProfileListener`, `inbox.service.ParticipantProfileService`, `inbox.domain.Participant.needsProfileRefresh` / `applyProfile`, `realtime.service.ParticipantRealtimeListener` | One adapter per channel hides Graph's profile endpoints and tokens from the inbox; the factory picks it by channel (a new channel is a new class). The shared base turns every Graph failure into an empty answer. An after-commit listener runs the lookup so the webhook never waits for Meta, and a published event lets the realtime listener tell open inboxes. The picture URL expires, so the same listener refreshes it by TTL on the next message and, bounded, after a history import. |
| Adapter + Factory + Template Method (history import) | `meta.service.ConversationHistoryClient`, `MessengerHistoryClient`, `InstagramHistoryClient`, `GraphHistoryClient`, `ConversationHistoryClientFactory`, `HistoryImportService` | The import reads past conversations through one interface and never sees Meta's JSON; the factory picks the adapter by channel and the shared base does paging and parsing. The service reuses `IncomingMessageService` so dedupe, linking and tenant scoping stay in one place. |
| Observer (history import trigger) | `meta.service.ChannelConnectedEvent`, `HistoryImportTrigger` (`@TransactionalEventListener`, `ApplicationReadyEvent`), `inbox.service.HistoryImportedEvent`, `realtime.service.InboxRealtimeListener` | Connecting an account only publishes an event; the import runs later on a bounded executor and cannot fail the request. One summary event, not one per message, tells open inboxes to refresh. |
